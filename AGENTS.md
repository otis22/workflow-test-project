# Руководство для ИИ-агентов

Краткий указатель правил и артефактов проекта. Агент обязан следовать workflow и обращаться к артефактам при планировании и реализации.

## Workflow

### 1. Workplan

- Workplan хранится в `Roadmap.md`
- Формируется агентами на основе PRD
- Содержит только:
  - название этапа / задачи
  - короткое описание этапа / задачи
  - статус
- Не содержит деталей реализации
- Является единственным источником очереди работ

### 2. Выбор задачи

Агент выбирает задачу по правилам:

- Только задачи со статусом `todo`
- Без незавершённых зависимостей
- Самая верхняя в списке

Запрещено:

- брать несколько задач
- перескакивать
- создавать новые задачи вне Workplan

### 3. Pre-task validation

Перед началом каждой задачи агент проверяет:

- CI на main зелёный
- Docker Compose поднимается без ошибок
- Нет незакоммиченных изменений от человека

Если среда сломана — сначала починить, потом работать. Починка среды не считается задачей из Roadmap.

Если есть незакоммиченные изменения — остановиться и уточнить у пользователя.

### 4. PRD задачи

Перед началом реализации агент обязан:

- Создать PRD задачи в `/PRD`
- Выполнить декомпозицию

Ограничения:

- Подзадача <= 2 человеко-часов
- Или <= 150 строк кода

Без декомпозиции реализация запрещена.

### 5. Core Loop агента

Агент работает только через цикл:

1. Выбрать подзадачу
2. Сделать короткий ресёрч
3. Написать тесты
4. Red -> Green
5. Запустить все проверки
6. Self-review кода
7. Commit
8. Codex review (через Codex плагин)
9. Проверка адекватности замечаний Codex (триаж)
10. Исправить принятые замечания + повторные проверки
11. Push
12. Дождаться CI

**ВАЖНО: шаги 1–12 обязательны и последовательны. Пропуск любого шага запрещён. Агент НЕ МОЖЕТ перейти к следующему шагу, не завершив текущий. Нарушение порядка = невалидный результат работы.**

#### Шаг 8 — Codex review (через Codex плагин)

После коммита, **перед push**, агент обязан запросить code review через Codex плагин.

**Процедура:**

1. Агент вызывает скилл `codex:rescue` с задачей провести code review diff'а текущей подзадачи
2. В промпте для Codex агент **обязательно** указывает:
   - Контекст задачи (что делали и зачем)
   - Ссылки на артефакты проекта: `artifacts/prd-taskflow-ru.md`, `artifacts/technical-requirements-taskflow-ru.md`, `artifacts/domain-model-taskflow-ru.md`, `artifacts/ui-spec-taskflow-ru.md`
   - Инструкцию: «Используй артефакты из `/artifacts` как источник требований при review — проверяй соответствие кода продуктовым требованиям, доменной модели, техническим ограничениям и UI-спецификации»
   - Просьбу проверить: качество кода, потенциальные баги, соответствие архитектуре проекта, читаемость, безопасность
3. Агент получает результат review от Codex и анализирует замечания

**Запрещено:**

- Пушить без прохождения Codex review
- Игнорировать замечания Codex — каждое замечание должно быть либо исправлено, либо аргументированно отклонено с записью причины в коммит
- Подменять Codex review собственным self-review (это разные шаги)

#### Шаг 9 — Проверка адекватности замечаний Codex (триаж)

Перед тем как исправлять что-либо, агент **обязан** провести триаж замечаний Codex. Codex может предлагать улучшения, которые не соответствуют контексту задачи, преждевременны, выходят за scope или противоречат артефактам проекта. Слепое применение всех замечаний приводит к scope creep и деградации архитектуры.

**Процедура триажа:**

Для каждого замечания агент классифицирует его в одну из категорий:

| Категория | Действие |
|-----------|----------|
| `accept` | Замечание корректно и в scope текущей задачи — будет исправлено на шаге 10 |
| `defer` | Замечание корректно, но выходит за scope подзадачи — оформляется как новая задача в `Roadmap.md` с пометкой `[review]` |
| `reject` | Замечание некорректно для контекста проекта (противоречит артефактам, преждевременная оптимизация, ложноположительное, дублирует уже принятое решение) — фиксируется обоснование |

**Критерии принятия решения:**

- Соответствует ли замечание PRD текущей подзадачи и её scope?
- Не противоречит ли оно артефактам в `/artifacts`?
- Не является ли оно преждевременной оптимизацией / абстракцией?
- Является ли оно реальным дефектом, а не стилистическим предпочтением?
- Реализуемо ли оно в рамках бюджета подзадачи (≤2ч / ≤150 строк)?

**Результат триажа** агент фиксирует кратким списком в теле commit-сообщения шага 10 или в `AssumptionLog.md`:

```
codex triage:
- accept: <короткое описание> — будет исправлено
- accept: <короткое описание> — будет исправлено
- defer: <короткое описание> — вынесено в Roadmap как [review]
- reject: <короткое описание> — причина: <обоснование>
```

**Запрещено:**

- Слепо применять все замечания без триажа
- Молча игнорировать замечания — каждое должно быть классифицировано
- Помечать как `reject` без обоснования
- Расширять scope текущей подзадачи через `accept` замечаний, выходящих за её границы (для таких — только `defer`)

#### Шаг 10 — Исправление принятых замечаний + повторные проверки

Если по результатам триажа есть замечания со статусом `accept`:

1. Агент исправляет код только по `accept`-замечаниям
2. Перезапускает все проверки (шаг 5)
3. Делает новый коммит с префиксом `fix: codex review — <описание>` и включает результат триажа
4. **Повторно** запрашивает Codex review для нового diff'а (возврат к шагу 8)
5. Цикл повторяется пока Codex не подтвердит отсутствие критичных замечаний

Если все замечания были `defer` или `reject` — агент сразу переходит к шагу 11 (Push), не делая дополнительных коммитов с правками.

**Бюджет итераций:** максимум 3 цикла review. Если после 3-й итерации остаются критичные замечания — агент останавливается, документирует ситуацию в `AssumptionLog.md` и уточняет у пользователя.

#### Шаг 6 — Self-review кода

Агент перечитывает diff своих изменений и проверяет:

- Код читаем? Имена переменных и методов понятны?
- Можно ли упростить? Нет ли лишней сложности?
- Нет мёртвого кода, неиспользуемых импортов?
- Соответствует стилю и conventions проекта?

Если находит проблемы — исправляет, перезапускает проверки (шаг 5), затем коммитит.

#### Шаг 12 — Ожидание CI

После push агент:

- Дожидается результата GitHub Actions
- Если CI упал — анализирует причину, исправляет, повторяет цикл с шага 5
- Не переходит к следующей задаче пока CI не зелёный

Запрещено:

- писать код без тестов
- пушить без прохождения локальных проверок
- пушить без прохождения Codex review
- игнорировать замечания Codex
- пропускать триаж замечаний Codex
- слепо применять все замечания Codex без триажа
- игнорировать упавший CI
- брать новую задачу при красном CI
- пропускать self-review
- пропускать Codex review
- менять порядок шагов Core Loop

### 6. Завершение задачи

После выполнения:

- Обновить статус в `Roadmap.md`
- Зафиксировать:
  - допущения
  - неясности
  - архитектурные решения

Всё записывается в `AssumptionLog.md`.

Задача считается завершённой только после записи в Assumption Log.

### 7. Периодический Review

#### Триггеры

- После завершения всех задач этапа в Roadmap
- Если прошло 5+ задач без review внутри этапа (счёт ведётся от последнего review)

#### Чеклист

| Аспект | Что проверяем |
|--------|--------------|
| Артефакты | Roadmap и PRD отражают реальность? Документация актуальна? Если пользователь вносил изменения в код — синхронизировать артефакты |
| Архитектура | Соответствует задачам и техническим требованиям? Нет дублирования? Нет признаков деградации или legacy? |
| Безопасность | Нет уязвимостей в новом коде? Валидация входных данных, авторизация, sanitization |
| CI/инфраструктура | CI работает стабильно? Нет warnings в логах? Тесты не flaky? |
| Зависимости | `composer audit` — нет known vulnerabilities? Критичные пакеты не устарели? |

#### Политика исправлений

- Найденные проблемы оформляются как новые задачи в Roadmap с пометкой `[review]`
- Берутся в работу в порядке общей очереди
- Обновление устаревшей документации делается сразу в рамках review, без отдельной задачи

#### Результат review

- Запись в `AssumptionLog.md` с итогами
- Новые задачи в `Roadmap.md` (если найдены проблемы)

### 8. Rollback-стратегия

Если задача оказалась тупиковой или ломает архитектуру:

- После 2–3 неудачных попыток решения — остановиться
- Документировать проблему в `AssumptionLog.md`
- Вернуть задачу в `todo` с пометкой `[blocked]` и причиной
- Не пытаться «дожать» бесконечно

#### Бюджет контекста задачи

- Если в ходе реализации задача превысила оценку в 2x (по строкам или по времени) — остановиться
- Передекомпозировать задачу, обновить PRD
- Разбить на более мелкие подзадачи

### 9. Smoke tests после этапа

После завершения всех задач этапа в Roadmap агент обязан запустить smoke tests:

- `docker compose up` — приложение поднимается без ошибок
- Основные URL отвечают корректно
- Если smoke test упал — исправить до перехода к следующему этапу

### 10. Changelog

После завершения этапа Roadmap агент генерирует краткий changelog:

- Что было сделано: фичи, фиксы, рефакторинг
- Формат: Markdown, файл `CHANGELOG.md` в корне проекта
- Используется для отслеживания прогресса и выявления scope creep

### 11. Артефакты проекта

Все управленческие артефакты ведутся в Markdown.

Обязательные файлы:

- `Roadmap.md` — Workplan
- `/PRD/*.md` — PRD задач
- `AssumptionLog.md` — журнал допущений
- `CHANGELOG.md` — changelog по этапам

ИИ-агенты не используют внешнюю память. Единственный источник контекста — файлы проекта.

### 12. Формат коммитов

Используется Conventional Commits:

- `feat:` — новая функциональность
- `fix:` — исправление бага
- `refactor:` — рефакторинг без изменения поведения
- `test:` — добавление или изменение тестов
- `docs:` — документация
- `chore:` — инфраструктура, зависимости, CI
- `review:` — исправления по результатам периодического review

Формат: `тип: краткое описание на английском`

## Справочные артефакты

В папке `artifacts/` хранятся исходные материалы проекта. Агент обязан обращаться к ним при формировании Roadmap, написании PRD задач и принятии архитектурных решений.

Текущий минимальный набор артефактов проекта:

| Файл | Назначение |
|------|------------|
| `artifacts/prd-taskflow-ru.md` | Продуктовое описание, цели MVP, user stories, функциональные и нефункциональные требования |
| `artifacts/technical-requirements-taskflow-ru.md` | Технические ограничения, стек, требования к архитектуре, тестам, качеству и CI/CD |
| `artifacts/domain-model-taskflow-ru.md` | Сущности, связи и базовые бизнес-правила домена |
| `artifacts/ui-spec-taskflow-ru.md` | Минимальное описание экранов, навигации и поведения интерфейса |

При нехватке данных агент сначала сверяет решение с этими артефактами, а затем уже принимает самостоятельные инженерные решения в пределах зафиксированных ограничений.

Если проект опирается на внешний API или внешний контракт, агент не домысливает его поведение и проверяет детали по спецификации или reference-артефактам из локальной папки `artifacts/`.

## Тесты и проверки

- Набор команд проверок должен быть явно описан в `README.md` или рядом с задачей.
- Задача не считается завершённой без прохождения проверок и записи в `AssumptionLog.md`.
