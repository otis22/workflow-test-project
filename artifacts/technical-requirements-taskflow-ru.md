# Технические требования: TaskFlow

## 1. Технологический стек

- PHP 8.3+
- Laravel
- Blade или другой встроенный серверный способ рендеринга интерфейса
- Реляционная база данных
- Docker Compose для локального окружения

Точные минорные версии агент может выбрать самостоятельно, если они совместимы между собой и стабильны.

## 2. Требования к архитектуре

- Проект должен следовать принципам чистой архитектуры.
- Бизнес-логика не должна зависеть от UI, фреймворка и инфраструктуры.
- Код должен быть организован так, чтобы доменные правила можно было тестировать изолированно.
- Допускается pragmatic Laravel-structure, если границы ответственности остаются явными.

Минимально должны быть различимы:

- доменная логика;
- сценарии приложения;
- инфраструктурный слой;
- web/UI слой.

## 3. Требования к качеству кода

- Код должен быть читаемым, с небольшими классами и методами.
- Следует избегать дублирования.
- Следует придерживаться SOLID и понятных именований.
- Следует минимизировать fat controller и fat model подходы.
- Решения должны быть достаточно простыми для MVP и не перегружены преждевременной абстракцией.

## 4. Обязательные инструменты качества

- Unit tests
- E2E tests
- Smoke tests
- Линтер/форматтер
- Статический анализ
- Rector
- Детектор копипасты
- Мутационное тестирование
- Проверка покрытия кода (coverage gate)
- Аудит зависимостей

Предпочтительный набор:

- PHPUnit или Pest (с генерацией coverage)
- Laravel Dusk или другой подходящий e2e-инструмент
- Infection (PHP Mutation Testing Framework)
- Laravel Pint
- PHPStan
- Rector
- PHPCPD или совместимый аналог
- composer audit

Агент может уточнить конкретный инструмент, если он лучше соответствует выбранной реализации.

## 5. Требования к тестированию

Unit tests должны покрывать:

- доменные правила;
- application services / use cases;
- критичные проверки входных данных и переходов состояния.

E2E tests должны покрывать:

- регистрацию;
- вход;
- создание проекта;
- создание задачи;
- изменение статуса задачи;
- просмотр списка своих задач.

Coverage:

- Минимальный порог покрытия для domain и application слоёв — 80%.
- Coverage не должен падать от коммита к коммиту (ratchet-принцип).
- Проверка покрытия должна быть частью CI-пайплайна и блокировать merge при нарушении порога.

Mutation tests:

- Запускаются на доменных правилах и application services.
- Минимальный MSI (Mutation Score Indicator) определяется после первого прогона.
- Цель — выявить слабые тесты, которые проходят при любых мутациях кода.

## 6. Требования к локальной среде

Локальная разработка должна запускаться через Docker Compose.

Минимально должны существовать сервисы для:

- приложения;
- веб-сервера;
- базы данных.

Дополнительные сервисы агент выбирает по необходимости.

## 7. Требования к CI/CD

GitHub Actions должны выполнять автоматические проверки.

Каждый инструмент из секции 4 должен быть представлен в CI. Агент обязан убедиться, что CI-пайплайн покрывает все обязательные инструменты качества.

### Основной CI-пайплайн (на каждый push/PR)

- установка зависимостей;
- запуск линтера/форматтера в режиме проверки;
- запуск unit tests с проверкой coverage (порог из секции 5);
- запуск статического анализа;
- запуск детектора копипасты;
- запуск rector в dry-run режиме;
- `composer audit` — проверка зависимостей на известные уязвимости.

### Дополнительные CI workflows

Следующие проверки допускается выносить в отдельные workflows, если это упрощает основной пайплайн:

- E2E tests (Laravel Dusk или аналог);
- Smoke tests (docker compose up + проверка ответа основных URL) — запускаются после завершения каждого этапа Roadmap;
- Мутационные тесты (Infection).

Каждый дополнительный workflow должен блокировать merge при неудаче.

### CD

CD может быть минимальным или отложенным, но структура проекта должна позволять его добавить без переделки архитектуры.

## 8. Требования к принятию решений агентом

Если артефакты не фиксируют точную реализацию, агент может самостоятельно принимать решения по:

- внутренней структуре каталогов;
- конкретным пакетам и библиотекам;
- устройству UI в рамках минимального описания;
- деталям CI/CD;
- выбору базы данных для локальной разработки.

При этом агент не должен нарушать ограничения этого документа и PRD.
