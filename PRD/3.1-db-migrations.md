# PRD: 3.1 — Миграции БД

## Цель

Создать миграции для 5 доменных таблиц (`users`, `projects`, `project_members`, `tasks`, `comments`), согласованных с доменными сущностями (stage 1). Это первый шаг infrastructure-слоя.

## Контекст

- Домен уже определён (stage 1): `User`, `Project`, `ProjectMember`, `Task`, `Comment`. Поля и типы — см. соответствующие `app/Domain/**/*.php`.
- Продакшн БД: **PostgreSQL 16** (см. `docker-compose.yml`, `.env` → `DB_CONNECTION=pgsql`).
- Тесты: **SQLite in-memory** (см. `phpunit.xml` → `DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`).
- Поэтому миграции должны быть совместимы с обеими СУБД — использовать Laravel Schema Builder (без raw SQL, без pg-specific типов).
- Существующая миграция `0001_01_01_000000_create_users_table.php` содержит Laravel-дефолты: `users` (с `email_verified_at`, `password`, `remember_token`), `password_reset_tokens`, `sessions`. Она не соответствует доменной модели — будет заменена.

## Scope

**В scope:**

- Замена дефолтной миграции `users` на domain-aligned: поля `name`, `email` (unique), `password_hash`, `created_at`, `updated_at`. Без `email_verified_at`, `remember_token` — эти Laravel-auth поля не используются (кастомный `SessionGuard`).
- Удаление таблицы `password_reset_tokens` из дефолтной миграции — восстановление пароля не входит в MVP (см. `artifacts/prd-taskflow-ru.md` §7 "Границы MVP").
- Сохранение таблицы `sessions` — Laravel session driver может её использовать (ортогонально нашему `SessionGuard`).
- 4 новые миграции: `projects`, `project_members`, `tasks`, `comments`.
- Foreign keys с `ON DELETE CASCADE` для связей, где это соответствует домену:
  - `projects.owner_id → users.id` — **RESTRICT** (нельзя удалить пользователя, пока он владеет проектами). Альтернатива — CASCADE, но это стирает проекты при удалении владельца; в MVP без soft delete это опасно. RESTRICT безопаснее, явное сообщение об ошибке.
  - `project_members.project_id → projects.id` — **CASCADE** (удалили проект → удалились членства).
  - `project_members.user_id → users.id` — **CASCADE** (удалили пользователя → удалились его членства).
  - `tasks.project_id → projects.id` — **CASCADE** (удалили проект → удалились задачи).
  - `tasks.creator_id → users.id` — **RESTRICT** (нельзя удалить пользователя, который автор задач; сохраняет историю).
  - `tasks.assignee_id → users.id` — **SET NULL** (удалили пользователя → задача осталась, но без исполнителя).
  - `comments.task_id → tasks.id` — **CASCADE** (удалили задачу → удалились комментарии).
  - `comments.author_id → users.id` — **RESTRICT** (сохраняет историю авторства).
- Индексы:
  - `project_members` — составной unique `(project_id, user_id)` (один пользователь не может быть участником дважды).
  - `tasks` — индекс на `project_id`, индекс на `assignee_id`, индекс на `status`, индекс на `due_date` (для `ListProjectTasks` фильтров).
  - `comments` — индекс на `task_id` (для `ListTaskComments`).
- Feature test, проверяющий структуру всех 5 таблиц: наличие, колонки, ключи, уникальность.

**Вне scope:**

- Eloquent-модели и репозитории (3.2).
- Фабрики/сидеры (3.3).
- Soft delete — не в MVP.
- Seed-данные.

## Тесты (Feature, использует in-memory SQLite)

- `tests/Feature/Database/MigrationsTest.php` — после `RefreshDatabase` проверяет:
  - Все 5 таблиц существуют.
  - Каждая таблица имеет ожидаемые колонки.
  - `users.email` — unique.
  - `project_members(project_id, user_id)` — unique.
  - Foreign keys работают (попытка insert с несуществующим FK бросает).
  - `ON DELETE CASCADE` для project_members при удалении project.
  - `ON DELETE SET NULL` для tasks.assignee_id при удалении user.
  - Отсутствие `email_verified_at`, `remember_token`, `password_reset_tokens` (проверка, что дефолтная миграция заменена).
