# PRD 2.r1 — Email normalization

## Источник
Codex review задачи 2.1 (см. AssumptionLog 1.2 / Roadmap 2.r1 [review]). Замечание: «Нормализовать email (lowercase + trim) на уровне use cases или value object EmailAddress. Сделать поиск дубликатов и login case-insensitive.»

## Цель
`Alice@Example.COM` и `alice@example.com` должны рассматриваться как один и тот же пользователь:
- При регистрации второго — `EmailAlreadyTakenException`.
- При login с любой case-варианцией — успешный вход.

## Решение
**Нормализация на границе use case** (lowercase + trim), не на уровне domain entity и не через введение `EmailAddress` value object. Обоснование выбора:
- Минимальный scope: 2 use case + тесты, без правок User entity, мапперов, миграций.
- Существующая позиция AssumptionLog 1.2: «transparency over speculative normalization» в domain — поэтому нормализация остаётся во внешнем слое.
- Введение `EmailAddress` VO потребовало бы менять User entity, маппер, фейки, миграцию (collation), 5+ тестов — выходит за scope ≤150 строк.

### Точки нормализации
1. `App\Application\User\RegisterUser::execute` — нормализовать перед валидацией формата, поиском дубликатов и сохранением. Сохранённый в БД email будет нормализованным.
2. `App\Application\Auth\Login::execute` — нормализовать перед `findByEmail`.

Реализация — приватный helper `private static function normalizeEmail(string $email): string` в каждом из двух классов (DRY-ratio для двух мест ниже порога вынесения в shared utility).

### Domain entity
`User::email` остаётся `string` без нормализации. Конструктор валидирует только формат. Это сознательно: ввод в User приходит уже нормализованным от use case (или из БД через маппер, где он был нормализован при записи).

`User::withEmail` тоже без нормализации — это domain-метод, не use case. Если в будущем появится use case `ChangeEmail`, нормализация будет в нём.

### БД
Существующий unique-constraint на `users.email` в pgsql case-sensitive — этого достаточно: после нормализации в use case все вставки идут в lowercase, дубликаты ловятся.

Существующих данных нет (миграции 3.1 свежие, продакшна нет) — миграция данных не требуется.

## Тесты (Red → Green)

### `tests/Unit/Application/User/RegisterUserTest.php`
1. `it('stores email in lowercase regardless of input case')` — register `Alice@Example.COM` → fake repo получает entity с `email = 'alice@example.com'`.
2. `it('detects duplicate email case-insensitively')` — register `alice@example.com` → register `ALICE@example.COM` бросает `EmailAlreadyTakenException`.
3. `it('trims whitespace around email')` — register `'  alice@example.com  '` → сохранённый email `'alice@example.com'`.

### `tests/Unit/Application/Auth/LoginTest.php`
1. `it('logs in with case-insensitive email')` — зарегистрирован `alice@example.com` → login с `'ALICE@example.COM'` успешен.

## Definition of Done
- 2 use case нормализуют email перед использованием.
- 4 теста (3 для RegisterUser + 1 для Login).
- `composer check:all` зелёный.
- Self-review, Codex review, триаж, push, CI.
